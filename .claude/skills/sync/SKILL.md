# /sync — Συγχρονισμός GitHub, σπίτι ↔ νοσοκομείο

## Η κεντρική ιδέα

Ο χρήστης δουλεύει σε **δύο μηχανήματα** και δεν γνωρίζει Git. Ο φόβος του είναι να
χάσει δουλειά· ο **πραγματικός** κίνδυνος είναι να κολλήσει σε μια σύγκρουση και να μην
ξέρει τι να πατήσει. Δουλειά σου είναι να το τακτοποιήσεις **και** να του πεις σε απλά
ελληνικά τι έγινε.

Η ασφάλεια δεν προκύπτει από εξυπνάδα, προκύπτει από **μία σειρά** που δεν παραβιάζεται:

> **1. Καταγράφω τα δικά μου → 2. Κατεβάζω τα ξένα → 3. Συγχωνεύω → 4. Ανεβάζω**

Μόλις κάτι γίνει commit, το Git δεν το χάνει ποτέ. Γι' αυτό η καταγραφή προηγείται
**πάντα** του κατεβάσματος. Ποτέ το ανάποδο.

Υπάρχουν **δύο repos** και συγχρονίζονται και τα δύο σε κάθε κλήση:

| | Τι | Πού |
|---|---|---|
| **Κώδικας** | `github.com/Bacilic/call_logger` | ο φάκελος του έργου (cwd) |
| **Μνήμη** | `github.com/Bacilic/call_logger_claude_memory` (ιδιωτικό) | `%USERPROFILE%\.claude\projects\<slug>\memory` |

## ΑΠΑΓΟΡΕΥΜΕΝΕΣ ΕΝΤΟΛΕΣ — απαράβατο

Αυτές οι εντολές **καταστρέφουν δουλειά χωρίς επιστροφή**. Δεν τις εκτελείς ποτέ μέσα
σε αυτή τη ροή, ούτε «για να ξεμπλοκάρει», ούτε αν φαίνονται η γρήγορη λύση:

- `git reset --hard` — πετάει αποθηκευμένες αλλαγές
- `git checkout -- <αρχείο>` / `git restore <αρχείο>` — γυρίζει αρχείο πίσω, σβήνοντάς το
- `git clean -f` / `-fd` / `-fdx` — διαγράφει αρχεία εκτός Git
- `git push --force` / `-f` / `--force-with-lease` — σβήνει δουλειά **του άλλου μηχανήματος** από το GitHub
- `git rebase` (και `pull --rebase`) — ξαναγράφει την ιστορία· ο χρήστης δεν μπορεί να ξεμπλέξει
- `git branch -D`, `git filter-branch`, `git reflog expire`, `git gc --prune=now`
- Διαγραφή ή «καθάρισμα» αρχείων με το χέρι για να περάσει ένα pull

**Αν κάποια από αυτές μοιάζει απαραίτητη, σταμάτα και ρώτα τον χρήστη.** Πάντα υπάρχει
ήπιος δρόμος. Η μοναδική επιτρεπτή «οπισθοχώρηση» είναι το `git merge --abort`, που
επαναφέρει τα πάντα ακριβώς όπως ήταν πριν τη συγχώνευση.

**Ποτέ δεν δημιουργείς νέο κλάδο (branch).** Ο χρήστης δουλεύει μόνο στο `main`· ένας
δεύτερος κλάδος θα του «εξαφάνιζε» τη δουλειά χωρίς να έχει τρόπο να την ξαναβρεί.

## Ροή εργασίας

### ΒΗΜΑ 0 — Χάρτης κατάστασης (πρώτα ο κώδικας)

Χωρίς αίτημα άδειας, μάζεψε την εικόνα και των δύο repos:

```
git status --short --branch
git fetch origin
git log --oneline HEAD..origin/main     # τι περιμένει να κατέβει
git log --oneline origin/main..HEAD     # τι περιμένει να ανέβει
```

Έλεγξε τρία «σταματήματα» πριν προχωρήσεις — αν ισχύει κάποιο, **μην αυτοσχεδιάσεις**,
περίγραψέ το και ρώτα:

1. **Δεν είσαι στο `main`** (ή detached HEAD) → σταμάτα. Ο χρήστης δεν το έκανε επίτηδες.
2. **Μισοτελειωμένη συγχώνευση** (υπάρχει `.git/MERGE_HEAD`) → προηγούμενη προσπάθεια έμεινε στη μέση· λύσε πρώτα αυτή (ΒΗΜΑ 3).
3. **Το `fetch` απέτυχε** → δίκτυο ή διαπιστευτήρια. Δες «Όταν κάτι πάει στραβά».

**Παρουσίασε την εικόνα στα ελληνικά, όχι σε ορολογία.** Παράδειγμα:

> Εδώ έχεις **4 αρχεία αλλαγμένα** που δεν έχουν καταγραφεί.
> Στο GitHub περιμένει **1 καταγραφή** από το άλλο μηχάνημα («Κατάσταση Lansweeper…»).
> Θα σώσω πρώτα τα δικά σου, μετά θα κατεβάσω το δικό του, μετά θα τα στείλω όλα.

Αν και τα δύο repos είναι καθαρά και συγχρονισμένα: πες το σε **μία γραμμή** και σταμάτα.
Μην εκτελείς τίποτα άλλο.

### ΒΗΜΑ 1 — Καταγραφή των τοπικών (το δίχτυ ασφαλείας)

Αν δεν υπάρχουν τοπικές αλλαγές, προσπέρασε στο ΒΗΜΑ 2.

**α) Δες τι πάει να μπει, πριν μπει.** Ο χρήστης δεν θα ελέγξει· εσύ θα ελέγξεις:

```
git status --short
git diff --stat
```

Ξεχώρισε στην αναφορά σου τα **νέα αρχεία** (untracked) από τα τροποποιημένα, και
**προειδοποίησε ρητά** αν δεις κάτι ύποπτο να μπαίνει στο repo:

- αρχεία βάσης (`.db`, `.sqlite`, `.sqlite3`), αντίγραφα ασφαλείας, εξαγωγές δεδομένων
- εκτελέσιμα ή χτισίματα (`.exe`, `.zip`, `build/`, `.dll`)
- **οτιδήποτε πάνω από ~5 MB**
- αρχεία με ονόματα τύπου `secret`, `token`, `credentials`, `.env`

Αυτά είναι σχεδόν πάντα λάθος και το `.gitignore` κάποια δεν τα πιάνει. Ρώτα πριν τα
συμπεριλάβεις. **Ποτέ μην ανεβάσεις πραγματικά δεδομένα ασθενών ή αντίγραφο βάσης
παραγωγής.** Αν εμφανιστεί κάτι τέτοιο, σταμάτα τη ροή και πες το καθαρά.

**β) Συνέταξε το μήνυμα καταγραφής.** Διάβασε το `git diff --stat` (και τα ουσιώδη
σημεία του `git diff` αν χρειάζεται) και γράψε μήνυμα **στο ύφος του έργου**:

- Πρώτη γραμμή: μία περιγραφική ελληνική πρόταση για το **τι άλλαξε θεματικά**.
  Ποτέ «WIP», «sync», «αλλαγές», «update».
- Αν οι αλλαγές είναι πολλές, μια κενή γραμμή και σύντομες παύλες με τα κύρια σημεία.
- Κλείσε με: `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`

Πες στον χρήστη ότι αυτή είναι **καταγραφή μεταφοράς**, όχι έκδοση: σκοπός της είναι να
μη χαθεί η δουλειά στο πέρασμα από μηχάνημα σε μηχάνημα.

**γ) Δείξε το μήνυμα και ζήτα έγκριση** πριν εκτελέσεις. Μόνο μετά:

```
git add -A
git commit -m "..."
```

(Για πολύγραμμο μήνυμα, γράψ' το σε αρχείο στο scratchpad και `git commit -F <αρχείο>` —
απόφυγε τα here-strings του PowerShell με ελληνικά.)

Από αυτή τη στιγμή **τίποτα δεν μπορεί να χαθεί**, ό,τι κι αν συμβεί παρακάτω.

### ΒΗΜΑ 2 — Κατέβασμα και συγχώνευση

```
git pull --no-rebase origin main
```

Το `--no-rebase` είναι **ρητό επίτηδες**: θέλουμε συγχώνευση, γιατί η συγχώνευση έχει
καθαρή έξοδο διαφυγής (`git merge --abort`), ενώ το rebase όχι.

Τρία δυνατά αποτελέσματα:

- **«Already up to date»** → τίποτα καινούριο. Προχώρα.
- **Fast-forward ή αυτόματη συγχώνευση** → τα δύο μηχανήματα άγγιξαν διαφορετικά σημεία, το Git τα ένωσε μόνο του. Πες πόσα αρχεία ήρθαν.
- **CONFLICT** → ΒΗΜΑ 3.

### ΒΗΜΑ 3 — Σύγκρουση (conflict)

Σύγκρουση σημαίνει: **και τα δύο μηχανήματα άλλαξαν το ίδιο σημείο του ίδιου αρχείου**.
Το Git αρνείται να μαντέψει. Δεν χάθηκε τίποτα — και οι δύο εκδοχές είναι εκεί.

Πες το ακριβώς έτσι στον χρήστη, με τα ονόματα των αρχείων και **τι κάνει το καθένα**:

> Το αρχείο X το πείραξες και στα δύο μηχανήματα, στο ίδιο σημείο. Στη δουλειά έγραψες
> Α, στο σπίτι έγραψες Β. Πρέπει να αποφασίσουμε τι μένει. Καμία από τις δύο εκδοχές
> δεν έχει χαθεί.

Μετά:

1. `git diff --name-only --diff-filter=U` για τη λίστα.
2. Διάβασε κάθε αρχείο σε σύγκρουση και **κατάλαβε και τις δύο εκδοχές** πριν προτείνεις.
3. Πρότεινε συγχώνευση εξηγώντας **τι κρατάς από πού και γιατί**. Στις περισσότερες
   περιπτώσεις σωστό είναι να κρατηθούν **και τα δύο** (π.χ. δύο ανεξάρτητες προσθήκες).
4. **Ζήτα έγκριση.** Ποτέ μην διαλέξεις μόνος σου όταν οι δύο εκδοχές λένε διαφορετικά
   πράγματα για την ίδια λειτουργία — αυτό είναι απόφαση προϊόντος, δική του.
5. Καθάρισε τα σημάδια `<<<<<<<`, `=======`, `>>>>>>>`, μετά `git add <αρχείο>` και
   `git commit` (μήνυμα: «Συγχώνευση …» με μία γραμμή για την απόφαση).

**Ειδική περίπτωση — `pubspec.lock`:** μη χειροκίνητη επίλυση. Κράτα μία εκδοχή και τρέξε
`flutter pub get` για να ξαναχτιστεί.

**Ειδική περίπτωση — `docs/Βελτιώσεις.md` και `assets/changelog.json`:** εκεί οι
συγκρούσεις είναι σχεδόν πάντα «προσθήκες και από τις δύο μεριές» → κράτα και τα δύο,
προσέχοντας τη σειρά προτεραιοτήτων και τα διπλά κλειδιά έκδοσης στο JSON.

**Αν μπερδευτείς ή ο χρήστης θέλει να το αφήσει:** `git merge --abort`. Επιστρέφει τα
πάντα ακριβώς όπως ήταν πριν, με τη δουλειά του άθικτη — και δοκιμάζετε αργότερα.

### ΒΗΜΑ 4 — Ανέβασμα

```
git push origin main
```

Αν απαντήσει **`rejected` / `non-fast-forward`**, σημαίνει ότι στο ενδιάμεσο ανέβηκε κάτι
άλλο. Η λύση είναι **επανάληψη των ΒΗΜΑΤΩΝ 2–4**, όχι `--force`. Ποτέ `--force`.

### ΒΗΜΑ 5 — Ο φάκελος μνήμης

Ίδια ακριβώς ροή, με `git -C "<διαδρομή>"` σε κάθε εντολή. Εντόπισε τη διαδρομή:

```powershell
$c = @("$env:USERPROFILE\.claude\projects\F--flutter-projects-call-logger\memory",
       "$env:USERPROFILE\.claude\projects\E--call-logger\memory")
$mem = $c | Where-Object { Test-Path "$_\.git" } | Select-Object -First 1
```

Αν δεν βρεθεί, ψάξε ευρύτερα σε `$env:USERPROFILE\.claude\projects\*\memory\.git` και
διασταύρωσε το `git -C ... remote get-url origin` με το `call_logger_claude_memory`.

Διαφορές από τον κώδικα:

- **Μήνυμα καταγραφής:** σύντομο, μία γραμμή (π.χ. «Ενημέρωση μνήμης — παγίδες συγχρονισμού»). Χωρίς `Co-Authored-By`, χωρίς σώμα.
- **Καμία προειδοποίηση για μεγάλα αρχεία** — είναι μόνο κείμενο.
- **Αν λείπει εντελώς το `.git`** (πρώτη φορά σε αυτό το μηχάνημα): μην κάνεις τίποτα. Πες στον χρήστη να τρέξει **μία φορά** το `ΠΡΩΤΗ_ΦΟΡΑ_στη_δουλεια.bat` που ζει μέσα στον φάκελο μνήμης.
- **Ποτέ μην ανεβάσεις πραγματικά μυστικά** (κωδικοί, tokens, διευθύνσεις παραγωγής) στη μνήμη — ισχύει ο κανόνας των ψεύτικων τιμών.

### ΒΗΜΑ 6 — Επαλήθευση και αναφορά

Και για τα δύο repos:

```
git status --short --branch
```

Πρέπει να δείχνει `## main...origin/main` **χωρίς** `ahead`/`behind` και **χωρίς**
αλλαγμένα αρχεία. Αν δεν είναι έτσι, **δεν τελείωσε** — πες τι απομένει, μην ανακοινώσεις
επιτυχία.

Η τελική αναφορά, σύντομη και σε απλά ελληνικά:

> ✅ **Κώδικας:** ανέβηκαν 4 αρχεία («…»), κατέβηκε 1 καταγραφή από το άλλο μηχάνημα.
> ✅ **Μνήμη:** συγχρονισμένη, τίποτα καινούριο.
> Και τα δύο μηχανήματα βλέπουν τώρα την ίδια δουλειά.

## Όταν κάτι πάει στραβά

| Σύμπτωμα | Τι σημαίνει | Τι κάνεις |
|---|---|---|
| `could not read Username` / παράθυρο σύνδεσης | Ο Git Credential Manager ζητά ταυτοποίηση | **Δεν πληκτρολογείς εσύ κωδικούς.** Πες στον χρήστη να ολοκληρώσει τη σύνδεση στο παράθυρο του Windows |
| `Could not resolve host: github.com` | Χωρίς δίκτυο, ή το VPN/firewall του νοσοκομείου | Πες το. Η **τοπική καταγραφή** (ΒΗΜΑ 1) έχει ήδη γίνει — η δουλειά είναι σώα, θα ανέβει μόλις υπάρξει δίκτυο |
| `Your local changes would be overwritten` | Έγινε pull με ακαταγράφητα αρχεία | Δεν χάθηκε τίποτα, το Git αρνήθηκε. Γύρνα στο ΒΗΜΑ 1 και κάνε καταγραφή πρώτα |
| `rejected` στο push | Ανέβηκε κάτι στο ενδιάμεσο | ΒΗΜΑΤΑ 2–4 ξανά. **Ποτέ `--force`** |
| `unrelated histories` | Δύο ξεχωριστά repos — κάτι έχει στηθεί λάθος | **Σταμάτα και ρώτα.** Μη χρησιμοποιήσεις το `--allow-unrelated-histories` μόνος σου |
| `index.lock exists` | Άλλο εργαλείο (Cursor/VS Code) κρατά το repo | Πες στον χρήστη να το κλείσει και ξαναδοκίμασε |

**Αν βρεθείς σε πραγματικά μπερδεμένη κατάσταση:** σταμάτα, μην «διορθώσεις» τυφλά.
Το `git reflog` κρατά κάθε προηγούμενη θέση για ~90 μέρες, άρα τίποτα δεν είναι οριστικά
χαμένο· απλώς η επαναφορά θέλει προσοχή και ρητή απόφαση, όχι αυτοσχεδιασμό.

## Πώς μιλάς στον χρήστη

- **Απλά ελληνικά.** «Καταγραφή» για το commit, «ανέβασμα» για το push, «κατέβασμα» για
  το pull, «συγχώνευση» για το merge, «σύγκρουση» για το conflict. Τον αγγλικό όρο τον
  δίνεις σε παρένθεση **μία φορά** αν χρειαστεί, όχι κάθε φορά.
- **Πάντα με αριθμούς:** πόσα αρχεία, πόσες καταγραφές, από ποιο μηχάνημα.
- **Ποτέ μη διαβεβαιώσεις χωρίς επαλήθευση.** «Ανέβηκαν» λέγεται μόνο μετά το ΒΗΜΑ 6.
- **Ό,τι δεν έγινε, το λες.** Αν ο κώδικας συγχρονίστηκε αλλά η μνήμη όχι, αυτό είναι
  μισή δουλειά και ανακοινώνεται ως μισή.
- **Καμία διάλεξη για Git.** Ο χρήστης δεν θέλει να μάθει Git· θέλει να μη χάσει δουλειά.
